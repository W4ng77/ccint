# 6. Core sampling principle

The original corpus and the interaction neighborhood are generated by different sampling processes.

The original corpus approximates:

\[
P(\text{post retrieved by configured source/query collection})
\]

The new neighborhood corpus approximates:

\[
P(\text{interaction observation} \mid \text{cyber seed})
\]

These populations must remain distinguishable.

Therefore:

- do not insert newly discovered neighborhood posts into the original analytical `posts` population in a way that changes historical corpus denominators;
- do not automatically run the standard relevance gate over descendants and then treat accepted descendants as new seed posts;
- do not let neighborhood expansion alter historical topic-count time series.

The interaction layer is a **conditional expansion around frozen seeds**, not a new pass of the original search pipeline.

# 7. Interaction storage design

Create two logically separate stores:

1. **raw API snapshots**
2. **derived normalized interaction edges**

Raw responses must be retained so edge derivation can be reproduced.

## 7.1 Raw snapshot table

Create an append-only table equivalent to:

`interaction_snapshots`

Minimum recommended fields:

| field | meaning |
|---|---|
| `snapshot_id` | unique snapshot identifier |
| `collection_run_id` | link to neighborhood collection run |
| `seed_post_id` | internal seed identifier |
| `seed_post_uri` | Bluesky URI |
| `endpoint` | API endpoint called |
| `request_params_json` | exact request parameters |
| `retrieved_at` | UTC retrieval timestamp |
| `http_status` | HTTP status |
| `success` | full request success |
| `partial` | partial result indicator |
| `error_type` | normalized error class |
| `error_message` | raw/normalized error text |
| `cursor` | pagination cursor if any |
| `page_number` | page index if used |
| `raw_payload` | verbatim API response |
| `raw_payload_sha256` | integrity hash |
| `git_commit` | code version |
| `collector_version` | collection implementation version |

Do not store only parsed fields.

If payloads are large, storage may be compressed, but decompression must reproduce the exact raw logical response content used for derivation.

## 7.2 Derived edge table

Create an append-only table equivalent to:

`interaction_edges`

Minimum recommended fields:

| field | meaning |
|---|---|
| `edge_id` | unique edge identifier |
| `snapshot_id` | source snapshot |
| `collection_run_id` | source run |
| `seed_post_id` | seed inducing this observation |
| `root_post_id` | conversation root if available |
| `source_post_id` | child/source post where applicable |
| `target_post_id` | parent/quoted post where applicable |
| `source_actor_id` | source actor |
| `target_actor_id` | target actor if applicable |
| `edge_type` | `author`, `reply`, `quote`, `repost` |
| `event_created_at` | event time if known |
| `observed_at` | snapshot retrieval time |
| `depth` | reply depth relative to seed/root |
| `derivation_version` | parser/deriver version |
| `code_commit` | code version |
| `metadata_json` | extra structured fields |

Do not invent relations not supported by source data.

# 8. Bluesky edge semantics

Use actual Bluesky semantics.

## 8.1 Authorship

\[
User \xrightarrow{authors} Post
\]

## 8.2 Reply

Primary post-level form:

\[
Post_{reply}\xrightarrow{reply\_to}Post_{parent}
\]

A user-user edge may be derived for analysis:

\[
User_A\xrightarrow{replies\_to}User_B
\]

but only if the underlying post-level relation is retained.

## 8.3 Quote

\[
Post_A\xrightarrow{quotes}Post_B
\]

Preserve both quote-post text and quoted-post context when available.

## 8.4 Repost

Represent:

\[
User\xrightarrow{reposts}Post
\]

Do not represent a Bluesky repost as a `Post -> Post` edge unless source data explicitly supports that relation.

# 9. Timestamp semantics

Keep **event time** and **observation time** separate.

For replies:

\[
event\_created\_at = reply.createdAt
\]

For quotes:

\[
event\_created\_at = quote.createdAt
\]

For reposts, if no repost event timestamp is exposed through the tested API path:

\[
event\_created\_at = NULL
\]

and:

\[
observed\_at = \text{snapshot retrieval time}
\]

Never substitute snapshot time for missing repost-event time.

Consequences:

- repost count can be used as a structural/snapshot feature;
- repost count cannot be treated as a time-local event count;
- reposts must not be included in temporal activity series unless a defensible repost timestamp becomes available later.

# 14. Interaction neighborhood definition

For seed \(p\):

\[
R_d(p)=\text{reply descendants within depth }d
\]

\[
Q(p)=\text{quote posts of }p
\]

\[
B(p)=\text{actors observed to have reposted }p
\]

Full structural neighborhood:

\[
N(p)=R_d(p)\cup Q(p)\cup B(p)
\]

Temporal interaction neighborhood:

\[
N^{time}(p)=R_d(p)\cup Q(p)
\]

because repost timestamps are unavailable.

# 15. Cyber-discourse boundary

A descendant does **not** need to independently contain a cybersecurity keyword.

Define:

\[
CyberNeighborhood(x)=1
\]

when \(x\) is connected through an approved interaction relation to a validated cyber seed.

Do not redefine:

\[
CyberNeighborhood(x)=KeywordMatch(x)
\]

Example:

Seed:

“Company X hit by ransomware”

Replies:

“Again?”

“Do we know whether customer data was affected?”

Both replies belong to the interaction neighborhood even if they contain no original cyber keyword.

This is a central methodological reason for neighborhood expansion.

This controls scope, privacy expansion, and topic drift.

# 22. Human annotation taxonomy

Do not begin with a forced binary `organic vs syndicated`.

Use two dimensions.

## Dimension A — actor/activity role

Recommended categories:

- `automated_feed`
- `organizational_broadcast`
- `news_media`
- `security_professional`
- `individual_participant`
- `unclear_other`

## Dimension B — interaction function

For interaction observations:

- `broadcast_or_repost`
- `substantive_reply`
- `information_seeking`
- `information_providing`
- `discussion_or_reaction`
- `unclear`

Actor role and interaction function are not the same thing.

A news account may participate in a substantive exchange.

An individual may simply repost/broadcast.

Keep the dimensions separate.

# 27. Conceptual measurement model

Use:

\[
X_t=D_t+H_t+\epsilon_t
\]

where:

- \(X_t\): observed cybersecurity-related activity
- \(D_t\): dissemination/broadcast component
- \(H_t\): human discussion component
- \(\epsilon_t\): ambiguous/noisy/unmodeled component

Treat this initially as a conceptual decomposition.

Do not claim it is an exact accounting identity unless the annotation taxonomy is empirically mutually exclusive and exhaustive.

# 29. Main scientific question

The central question is:

> Does interaction-aware measurement change what a cybersecurity social sensor appears to observe?

Compare:

\[
S^{post}_{k,t}
\]

\[
S^{actor}_{k,t}
\]

\[
S^{interaction}_{k,t}
\]

and, where valid:

\[
S^{human}_{k,t}
\]

\[
S^{broadcast}_{k,t}
\]

The goal is not to find which signal is numerically largest.

The goal is to determine whether different signals support different substantive interpretations.

Possible divergence pattern:

\[
\Delta S^{post}_{k,t}>0
\]

while:

\[
\Delta S^{human}_{k,t}\approx0
\]

This would be consistent with increased dissemination without a corresponding increase in human discussion.

The reverse may also occur.

Do not assume either pattern in advance.

# 33. Initial model family

Start with simple baselines:
- logistic regression
- linear classifier over embeddings
- gradient-boosted trees where appropriate

A pretrained language-model classifier may be added later if justified.

Do **not** begin with a GNN.

Only consider graph neural networks if:
1. interaction structure is sufficiently dense;
2. simple interaction features contain useful information;
3. a specific unresolved hypothesis requires message passing;
4. the evaluation design can distinguish graph benefit from actor memorization.

Complexity itself is not methodological novelty.

# 36. Interpreting ablation

Do not define success as “full model has highest F1.”

Valid outcomes include:

### Outcome A
Interaction provides additional predictive information beyond content/actor features.

### Outcome B
Interaction has modest predictive value but substantially changes the measurement interpretation.

### Outcome C
Interaction adds little, and post-level measurement appears adequate for this corpus.

### Outcome D
Interaction is too sparse to estimate reliably.

All are scientifically valid.

# 48. Interpretive discipline

Preserve these rules throughout the project.

1. Volume is not automatically attention.
2. Platform-visible activity is not public opinion.
3. Event visibility is not human discussion.
4. Non-feed is not automatically organic.
5. Human-authored is not automatically conversational.
6. Movement is not a trend unless statistically supported.
7. Collection failure is not zero interaction.
8. External labels must not depend on the system being evaluated.
9. Repost observation time is not repost event time.
10. Annotation versions are never overwritten.
11. Every reported number names its denominator.
12. Small event samples require absolute counts.
13. Negative/null results are scientifically valid.
14. Do not make causal claims from observational associations.

# 51. Decision gates

## Gate A — Pilot collection quality

Proceed to full collection only if:
- API reconstruction is reliable;
- errors are measurable;
- partial retrieval is distinguishable;
- pagination works;
- derived edges are reproducible.

Otherwise stop and repair collection.

## Gate B — Interaction prevalence

If very few seeds produce replies or quotes:
- do not force an interaction-classification study;
- report interaction sparsity as a finding about the platform's suitability as a human-discussion sensor.

## Gate C — Annotation reliability

If human agreement is weak:
- do not present `S_human` as a validated measurement;
- refine taxonomy or restrict claims.

## Gate D — Predictive information

If interaction features provide no improvement:
- do not automatically escalate to GNNs;
- continue the measurement comparison.

## Gate E — Measurement divergence

If post, actor, and interaction measurements largely agree:
- report that simpler measurement may be adequate for this corpus;
- do not manufacture divergence.

# 52. Valid final outcomes

The study must permit all of these outcomes:

### A
Interaction-aware measurement substantially changes the observed cybersecurity picture.

### B
Interaction adds predictive information but aggregate conclusions remain similar.

### C
Interaction changes some topics/events but not others.

### D
Post-level measurements are largely adequate.

### E
Human interaction is too sparse for reliable discussion sensing.

### F
Evidence is insufficient because of sample size, collection limits, or annotation uncertainty.

All are valid if rigorously supported.
